# 飞书通知使用教程 · 0.9.2 实验版

本版把已验证的「可见通知区域截图 → 本机文字识别」接到桌宠，不需要飞书账号、机器人或 API Key。它只能识别屏幕上实际展示的部分，不能获取所有私聊、恢复隐藏消息或读完整聊天记录。

## 1. 从新版文件夹启动

退出旧 0.8.0 应用，保留旧文件夹。下载需要的独立版，解压到新文件夹：

- [海洋独立版 0.9.2](https://github.com/jianingecho-ctrl/AI-Coding/archive/refs/tags/ocean-v0.9.2.zip)
- [甄嬛传独立版 0.9.2](https://github.com/jianingecho-ctrl/AI-Coding/archive/refs/tags/palace-v0.9.2.zip)

源码 ZIP 不是安装包。已装 Node.js 24 LTS 的 Mac，可以双击本版启动脚本；首次启动会安装依赖并构建本机识别模块。需要 macOS 15.2+ 和带 macOS 15.2+ SDK 的 Apple 命令行开发工具或 Xcode。此前独立验证工具能编译的机器通常具备所需工具，新版仍会检查并显示具体错误。

脚本被系统阻止时，打开终端：输入 `cd` 加一个空格，把**新版文件夹**拖入终端，按回车。海洋版运行：

```bash
bash ./启动海洋版.command
```

甄嬛传版运行：

```bash
bash ./启动甄嬛传版.command
```

不要在旧目录启动，也不要把命令输入正在运行 `npm run dev` 的终端。需要新终端窗口时按 Command+N。每条命令单独粘贴，按回车后等待执行完成。

也可在新版目录手动执行：

```bash
ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/" npm ci
npm run build
npm start
```

控制台左下角应显示 0.9.2。新版沿用本版 0.8.0 的独立数据目录，原有联系人、人物、消息与互动次数会保留，两版之间不共享。

### 旧 0.9.0 原生构建中断的原地修复

如果已经下载 0.9.0，且报 `native/build.sh: line 18: architecture?: unbound variable`，说明 Swift 编译已结束，后面的成功提示遇到 Bash 3.2 中文变量边界问题。无需重新安装依赖。在旧 0.9.0 目录执行下面一行，会备份原脚本并替换该提示，再运行启动脚本：

```bash
/usr/bin/sed -i .before-fix 's/echo "原生通知识别模块已构建：.*"/echo "Native notification module built successfully"/' native/build.sh
bash ./启动海洋版.command
```

甄嬛版第二行使用 `bash ./启动甄嬛传版.command`。这是修复旧包的操作，旧包版本仍显示 0.9.0；0.9.1 及以后已内置修复。不要在正在运行应用的终端里输入命令，先退出或另开终端窗口。

## 2. 给实际发送人绑定人物

海洋版打开「联系人」，甄嬛版打开「宫中名册」，点一个联系人的「自定义效果」。

- 「显示姓名」是桌宠上展示的名字，可继续用人物名字。
- 「通知姓名别名」填写飞书通知里的发送人姓名，每行一个，例如 `小林 Lin`，然后保存。
- 选择本版人物和进场方式，播放预览后保存。

通知中「测试项目群」是群名，`小林 Lin：请交测试稿` 里的「小林 Lin」才是发送人。不要把群名填成姓名别名。不同联系人不要配置同一个别名；同名会留待人工确认。

## 3. 先验证一条通知

1. 打开海洋版「飞书通知」，或甄嬛版「飞鸽传书」。默认暂停、人工确认。
2. 默认选区为主屏幕右上角 480×360 点。让一条虚构内容的飞书通知在这里保持可见；可调整飞书通知为横幅或提醒，并在系统通知设置中允许预览。
3. 选择「5 秒后识别」或「10 秒后识别」，点「识别一次」，在准备时间内展开通知并把控制台移出选区。支持自定义选区，坐标和宽高单位是**屏幕点**，不是 Retina 像素。
4. 若提示未获得录屏权限，在系统设置 → 隐私与安全性 → 屏幕与系统音频录制，允许系统提示的**当前应用**，按系统要求退出并重新打开。源码运行通常显示 Electron，打包后显示本版应用；此前终端获得权限不等于 Electron 已获权限。此功能无需辅助功能或麦克风权限。
5. 「待确认通知」应展示姓名、群名、正文、置信度和对应联系人。核对或修改正文，选好联系人，点「确认送达桌宠」。
6. 桌宠应切换到这个联系人的人物、播放进场并显示消息卡片。卡片明确标注「屏幕通知识别 · 人工确认」和「本地规则摘要 · 未调用 AI」。

0.9.2 的「本轮结果」会显示文字行数、解析消息数、重复数和自动送达数，并提供「查看本轮识别的原始文字」。如果里面是桌面文件名、小判官自己的界面或其他应用，说明区域被遮挡或没有对准通知，先移开窗口或调整选区。普通桌面内容不会凭空生成未知联系人消息，混入自身界面的候选不会自动送达。原始文字仅存内存，清空草稿时一并清除，未确认内容不会写入历史。

只识别出区域文字但找不到姓名与正文时会提示；不会假装已接收到消息。没有识别到文字也不代表没有新消息。同一内容短时间重复识别会过滤，点了「忽略」也不会马上再次出现；测试时换一条正文。

## 4. 持续监测

一次识别成功后，点「开始监测」。第一次扫描只把当前屏幕上的已有通知作为基线，**不会重放旧通知**。0.9.2 需要核对这些尚未处理的已有通知时，可以暂停后点「识别一次」；已确认或已忽略的内容仍会去重。随后出现的新内容才进入待确认列表，默认每 3 秒识别一次。可以最小化控制台，让通知保持可见，稍后回到控制台确认。

希望直接触发人物时，勾选「匹配明确的通知自动送达桌宠」，保存设置，再点「开始监测」。仅在以下条件都满足时自动送达：

- 公开窗口信息符合系统通知或飞书小弹窗特征；系统通知还须识别到单独的飞书/Feishu/Lark 应用标题。
- 姓名或别名唯一匹配一个联系人。
- 识别置信度至少 90%。

来源不明、未绑定联系人、同名、置信度不足、混入自身界面或多张分行卡片的分隔不明确时，仍留在待确认列表。0.9.2 会将重复姓名或不同已绑定姓名的多张「姓名／正文」卡片分开；仅凭文字分隔无法确认卡片边界，需要先核对。窗口特征是辅助判断，并非官方消息认证；实际 Mac 上可能只能进入人工确认，这时不应放宽来源判断。

「暂停识别」停止后续捕获。「清空草稿并暂停」丢弃当前草稿并停止。关闭控制台窗口会保留桌宠和已启动的监测；要停止请点暂停或退出应用。每次重启都保持暂停，需要主动开始。

## 5. 卡片交互与回复

肘击、扇嘴、烧心、比心继续显示对应效果、声音和当天次数。互动不会通知真实联系人。

点「回复消息」，填写草稿并保存，再点「复制回复」。回到飞书的正确聊天，手动粘贴、检查并发送。小判官不会替你发送。点「查看通知内容」核对已识别的可见文本，完整原文仍需在飞书查看。

## 6. 数据和实际范围

区域截图只在内存中处理，不写入文件。识别草稿最多 20 条、仅保存在内存中，退出即清除；确认送达后才进入本版历史，最多 200 条。真实通知始终使用本机规则，不调用外部模型，即使模拟消息页已开启在线 AI。两版联系人、通知设置、历史、互动与密钥完全独立。

「消息历史／往来书信」可清空历史，同时清除当前卡片、草稿并暂停识别。互动统计另行清除。应用不读取飞书或系统通知数据库、不接入账号，不获取隐藏、截断、未出现于选区的消息；区域可能包含其他应用文字，因此务必先核对来源。

没有飞书消息 ID，使用姓名、群名和正文去重；连续可见的相同通知不会反复触发。短时间完全相同的两条真实消息可能被合并。多条通知同时出现时历史可以保留各条，桌面卡片展示最近送达的一条，可从历史恢复其他卡片。

## 7. 本机验收与打包

云端已用虚构 OCR 结果验证两版 Electron 的确认、自动送达、基线、去重、暂停、互动计数、复制和重启，并检查代码、构建与数据隔离；云端没有 macOS，未编译新版原生模块，也未验证真实通知窗口特征。

你的 Mac 需验收：原生编译、当前应用录屏权限、单聊与群聊文字、自动模式来源判断、多屏选区、窗口遮挡、中文识别质量、真实音效，以及打包安装。先用虚构消息完成步骤 3，再开始日常使用。

在本版 Mac 目录执行 `npm run pack:mac`，会构建 arm64/x64 识别模块并分别放入对应应用资源，输出本版 `release/ocean/` 或 `release/palace/` 的 DMG/ZIP。开发包未签名、公证；没有在云端生成或验证可安装的 Mac 包。完整安装步骤见 [Mac 教程](Mac使用教程.md)。

## 为什么识别到联系人却没有人物进场？

先看控制台显示的「当前送达模式」。默认人工确认，需要在草稿选择联系人并点「确认送达桌宠」；草稿不是已经送达的消息。勾选自动送达后需保存设置并开始监测，再发一条新测试消息。

联系人名单中存在这个人，不等于 OCR 姓名已匹配；草稿下拉框显示「请选择联系人」就表示未获得唯一匹配。在联系人编辑中填写屏幕识别出的完整姓名别名；字母 l/I 与数字 1 误识别时不要自动猜测是谁，由本人核对后添加别名。来源、置信度、分隔或遮挡不明确时仍需确认。
