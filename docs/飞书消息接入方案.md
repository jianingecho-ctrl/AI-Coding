# 飞书消息接入方案

V1.0 是产品阶段，开发版 0.8.0 的海洋独立版与甄嬛传独立版继续使用模拟消息，分别保存配置、历史和互动统计；V1.1 的真实飞书接入仍处于调研阶段。

## V1.0：模拟数据

- 测试面板选择联系人、输入模拟内容，点击「发送测试消息」走完整流程：联系人匹配 → 规则/AI 分析 → 本地历史 → 人物进场 → 消息卡片。
- 一键播放七类人物的默认进场，可以停止；演示使用临时联系人，不修改实际名单，不写历史，不调用 AI。
- 消息处理独立于 Electron 窗口和人物动画。`electron/messages.ts` 提供 `MessagePipeline`；展示层消费统一 `Message`。
- 当前入口只接受 `mock` 来源，按本地联系人 ID 匹配，避免同名误识别。没有机器人连接、真实飞书账号登录或 macOS 通知读取能力。
- 联系人、历史和模拟回复默认在本机保存。AI 默认关闭，使用明确标注的本地规则解析。
- 在线 AI 只发送当前输入的消息正文、模型参数及摘要提示到用户配置的地址；名单、历史、回复和人物素材不上传。正文中主动输入的信息仍属于外发内容。
- 提供关闭 AI、清空历史。清空后移除桌面与最近判读里的历史内容，并取消未完成解析的历史写回。

## V1.1：授权范围内的真实消息

优先采用企业自建机器人 + 消息事件订阅，研究长连接方式。官方 SDK 的 `WSClient` 和 `im.message.receive_v1` 已确认存在；SDK 说明长连接可在本地接收事件，无需公网回调地址。没有实际接入企业应用，消息权限范围与管理员审批尚未验证。

落地前必须完成：

1. 确认公司允许创建或安装应用，由企业管理员审核必要权限、可见范围和数据用途。
2. 使用虚构内容的测试群及机器人单聊，验证该应用能接收的消息类型与范围。
3. 按事件发送者的稳定用户 ID 绑定本地联系人，姓名作为显示字段。未知发送者的绑定与默认 NPC 行为需在这一阶段确定。
4. 将获授权事件转换为标准消息入口，再复用现有解析、配置、卡片和动画。对重复事件按消息 ID 去重；接收事件与耗时 AI 分析分离，避免超时重推。
5. 官方 SDK 提示同一应用的多个长连接客户端会随机分配事件，而非广播。多人桌面部署前需研究企业受控路由与身份隔离，不能简单让所有 Mac 共用同一连接方案。
6. 用测试结果确认发送者 ID、文本/富文本、群聊/单聊、断线重连、重复事件、权限撤销和应用发布后的行为。

官方机器人事件不能默认获取员工个人飞书账号收到的全部私聊。接入长连接解决的是事件传输方式，不会扩大读取权限。

macOS 通知仅作为待调研路线。需要核实公开接口、明确授权、飞书通知内容的可用性及企业政策；尚未证明有合规且可靠的跨应用读取方式。本版不读取通知，不抓取聊天客户端，不绕过企业权限。

真实公司消息接入前还应核实外部 AI 的企业数据政策。机器人获准读消息，并不自动代表消息可以发给外部模型。
