# 飞书消息接入方案 · 0.9.3

消息来源与人物动画解耦：`MessagePipeline` 接受模拟消息和经确认的可见通知，输出同一种结构化卡片。真实账号或官方机器人尚未接入。

## 已实现：模拟消息

测试面板选择联系人、输入正文，触发解析、人物、历史和互动；七人演示只预览，不写历史、不调用 AI、不计数。模拟消息默认本地规则，可主动配置本机 Ollama 或 OpenAI 兼容服务；在线服务只接收当前正文、模型参数和摘要提示，不上传名单、历史、回复和素材。关闭 AI 和清空历史均已实现。

## 已实现的实验接入：可见通知 OCR

用户在 Mac 上运行独立验证工具，已确认可以识别通知中的姓名与正文。0.9.3 将这条路径接到两个独立桌面应用：公开 ScreenCaptureKit 区域截图 → 本机 Vision 中文识别 → 来源提示 → 姓名/别名匹配 → 人工确认或满足严格条件后自动送达 → 本地规则 → 本版人物和卡片。

- macOS 15.2+；Apple 工具和 SDK 构建原生模块；当前应用获得系统录屏授权。
- 默认暂停、人工确认；主动开始后首轮内容作为基线，重启仍暂停。
- 选区为主屏右上角或自定义坐标，截图只在内存中处理，不保存。
- 基于公开窗口信息辅助判断来源。系统通知还需独立飞书应用标题，飞书小弹窗需符合进程标识及尺寸特征；自动送达还要求唯一联系人和至少 90% 置信度。无法判断或同名留待确认，窗口特征不是官方认证。
- 群通知按「姓名：正文」拆分，排除重复群名和明确界面文字。群名不是发送人。
- 姓名、群名、正文联合短时去重；没有消息 ID，完全相同的消息可能被合并。
- 草稿仅在内存中保留最近 20 条，确认后进入本版最多 200 条历史。暂停、退出、清除取消待完成捕获，清空历史也清空草稿并暂停。
- 真实通知始终本机规则解析，明确标注未调用 AI；即使模拟页开启在线 AI 也不会将通知发给该服务。
- 回复仅保存草稿、复制到剪贴板，由用户在飞书核对并手动发送；趣味互动不发送给真实联系人。

只能处理可见内容，不能补全隐藏、截断、未展示的消息，也不能保证识别每条短暂横幅。选区可能包含其他应用文字，须先核对。通知监测是截图识别实验，不等于系统允许第三方读取全部通知数据库或飞书个人收件箱。应用不查询这两类数据库，不抓取后台聊天。

两版通知配置、运行状态、草稿、历史和联系人隔离，不改变各自人物系统。使用与 Mac 验收步骤见 [飞书通知使用教程](飞书通知使用教程.md)。

已验证：单元测试、TypeScript/生产构建、Linux 上实际 Electron 窗口的虚构 OCR 夹具交互，以及双版本隔离。未验证：新版 Swift 原生编译、当前 Electron/打包应用录屏授权、Mac 通知窗口特征和多屏、真实通知端到端、签名/公证与 DMG 安装。此前 Mac 验证工具的成功不能代替这些新增验收。

## 后续独立路线：企业授权机器人

优先使用企业自建机器人和消息事件订阅。官方 Node SDK 提供 `WSClient`、`im.message.receive_v1`；长连接可本地接收事件，无需公网回调地址，但不会扩大读取权限。没有实际接入企业应用，管理员授权与消息范围仍待验证。

落地需要：企业管理员审核权限和可见范围；测试群及机器人单聊核对可接收消息；用稳定发送人 ID 绑定联系人；按消息 ID 去重；验证断线、重推、权限撤销和应用发布。同一应用的多个长连接可能随机分配事件，企业多用户部署还需受控路由设计。

官方机器人不能默认获取员工个人飞书账号收到的全部私聊。获准读取消息也不自动代表获准发送至外部模型。不会绕过企业权限抓取聊天内容。
